# F2 Ultra G-code dialect (verified samples)

Sources, all generated by xTool Studio 1.9.11 for the user's F2 Ultra:
- **Text export:** `captures/gc/blue_cut_70p_40mms_1pass.gc`, a 20 mm square, blue, 70%, 40 mm/s, 1 pass.
- **Text export:** `captures/gc/red_cut_70p_40mms_8pass_65khz_200ns.gc`, the same square on red, 8 passes, 65 kHz, 200 ns.
- **Text export:** `captures/gc/blue_fill_90p_1250mms_100lpcm.gc`, a filled 20 mm square, blue, 90%, 1250 mm/s, 100 lines/cm, zigzag.
- **Text export:** `captures/gc/blue_image_90p_200us_180dpi_jarvis.gc`, a 76×57 mm photo, blue, 90%, dot mode, 200 µs dots, 180 dpi, Jarvis dithering.
- **Binary job:** `captures/jobs/*_blue_VECTOR_CUTTING-70p-40mms-x8/motion.bgcode`, a star outline, blue, 70%, 40 mm/s, 8 passes. It was pulled from the device's `tmp.xf` and decoded with `pcprobe.bgcode`.

The two agree token for token, which confirms the binary decoder.

## Binary encoding (`motion.bgcode`)

The binary file is tokenized text, one line per `0x0A`:

| Byte | Meaning |
|---|---|
| `0xE1`–`0xFA` | letters A–Z (`0xE7` = G, `0xED` = M, `0xF8` = X) |
| `0x00`–`0x99` | packed BCD digit pairs, zero-padded (`X0143.6740`) |
| `0xCE` | `.` |
| `0xC0` | space |
| `0xC2` | `"` |
| `0xCD` | `-` (assumed, not yet seen) |
| `0xC3` | `#`; the rest of the line is raw ASCII |

The device also accepts plain text (`gcodeFormat` includes `txt`), so we can send text.

## File structure

```
# date=… / version=1.9.11 / algorithmVersion=
# gc={"size":{"w":220,"h":220}}          work area
# gc={"offset":{"x":0,"y":0}}
# gc={"start":{"x":0,"y":0.0000}}
# gc={"keys":["x","y"],"rm":1,"is3DMode":false}
# timeConfig=
G90
G0 F3000
G4P5
G198 P84 "M9033 V100"                   ┐
G198 P85 "M9401 D2 V500"                │ machine setup preamble (?): likely air assist,
M9064 B3 / G198 P70|P78 "M9064 B3"      │ fan and purifier gears per peripheral port P.
M9039 C2 / G198 P69 "M9039 C2"          │ G198 P<n> "<cmd>" seems to forward a command
G198 P76 "M9039 V50"                    │ to accessory n. Copy verbatim until understood.
G198 P76 "M9043 H11 I11 J11 K11 L11 M11"┘
G4P5
# GS004-4 HEAD
G0 F180000          rapid (jump) speed 3000 mm/s
M4 S0
G1 F180000
G0 X0 Y0
# GS004-4 VECTOR HEAD
# motion_start
G4P1
G21 | G22           G21 = blue diode, G22 = red fiber (verified)
[G0H<pulseWidth ns>]   red only, e.g. G0H200
[G0Q<freq kHz>]        red only, e.g. G0Q65
G90
G4P1
M523P40             P40 = vector mode (P10 = dot/bitmap?)
[# MUST / G104 P<passes>]        only when passes > 1
# blockConfig={"powerFactor":0.7,"isVector":true,"crossDot":false}
G0X100Y100                       jump to the start of the path
G1X120Y100S700F2400              S = power % ×10, F = speed mm/s ×60
G1X120Y120                       S and F are modal
G1X100Y120
G1X100Y100
[# MUST / G105]                  end of the pass loop
# GS004-4 VECTOR TAIL
# motion_end
# END
# GS004-4 TAIL
G90
G0 S0
G1 F180000
M536 U0
M6 P1
```

**Coordinates** are absolute, in mm, inside the 220×220 field. The square drawn at canvas x=100, y=100 appears as X100 Y100, so canvas coordinates map 1:1.

For red, the only differences are `G22`, `G0H200` (pulse width in ns) and `G0Q65` (MOPA frequency in kHz) right after `G90`. S and F are scaled the same way for both lasers.

**Passes** are a loop **per path block**. With 8 passes and several paths, path A runs 8 times, then path B runs 8 times. This is why a single job can't pause between passes of the whole job. We can choose a different loop structure: either one loop around all paths, or one file per pass.

**`blockConfig.powerFactor`** is power / 100. The border (framing) file uses `S64` with `powerFactor 0.064`, which is a framing laser power of about 6.4% (the setting `customWalkBorderData.power` is 4).

## Fill engraving (verified)

```
# GS004-4 BITMAP HEAD          fill uses the BITMAP block type, not VECTOR
# motion_start
G4P1
G21
G4P1
M523P40                        still P40 (not P10) for fill
# blockConfig={"powerFactor":0.9,"overDist":0,"accel":5000,"density":10,"power":[0,900],"bitmapMode":"grayscale","crossDot":false,"startX":0,"isVector":false}
G1F75000S0                     1250 mm/s × 60; laser off
G0X100.000Y100.000             jump to the first line
G1X120.000S900                 burn line 1 left→right
G1Y100.100S0                   step 0.1 mm with the laser off (G1, not G0)
G1X100.000S900                 burn line 2 right→left (zigzag = bitmapScanMode "zMode")
...                            200 lines, Y100.000 to Y119.900
# GS004-4 BITMAP TAIL
# motion_end
```

- **Line spacing** is 10 / (lines per cm) mm, so 100 lines/cm gives 0.1 mm. `blockConfig.density` is in lines per mm.
- **Line count:** a 20 mm square gets exactly 200 lines. The last line is at Y+19.9, not Y+20.
- **Overscan:** `overDist: 0`, so lines start and stop exactly at the shape edge. Overscan presumably extends each X line beyond the edge with S0.
- **Coordinates** are written with 3 decimals here, unlike vector moves.
- **Preamble difference:** fill jobs end the preamble with `G198 P76 "M9043 H1 I1 J1 K1 L1 M1"`, where vector cuts use `H11 … M11`. **Not air assist** (the user has none). It may be a flame-sensor sensitivity setting per processing type (?). We copy it as-is: H11 for cuts, H1 for fills and bitmaps.

## Bitmap engraving, dot mode (verified)

```
# GS004-4 BITMAP HEAD
# motion_start
G4P1
G21
G4P1
M523P10                       P10 = dot mode (vector and fill use P40)
# blockConfig={"powerFactor":0.9,"overDist":0,"accel":5000,"density":7.0866,"power":[10,900],"bitmapMode":"Jarvis","crossDot":false,"startX":0,"isVector":false}
G1F4800S0                     travel speed between dots: 80 mm/s × 60 (the profile's speed)
G25T20                        dot duration: 200 µs → T20 (units of 10 µs, assumed)
G0X72.013Y81.510              jump to the first dot
G25X72.013Y81.510S900         G25 = move there and fire one dot; S is modal
G25X72.154                    next dot, 0.141 mm = 25.4/180 to the right
G25X72.436                    white pixels are simply skipped (bigger X step)
...
G25X147.507Y81.651            new row: move diagonally to the first black dot of the next row
G25X147.366                   rows alternate direction (zigzag)
```

- **Everything is `G25`.** There is exactly one `G0` (the first jump) and one `S` value, so every dot fires at the same power. Jarvis is a binary dither: the image's tone comes from dot *density*, not from varying power. `power:[10,900]` (min/max) is presumably used only by grayscale mode.
- **Row starts:** each row begins at its first black pixel in the travel direction. Empty leading and trailing pixels are not visited.
- **Pitch** is 25.4 / dpi in both X and Y. Coordinates are rounded to 3 decimals, which is why steps alternate between 0.141 and 0.142 mm. `blockConfig.density` is dots per mm (180 / 25.4 = 7.0866).
- **Size:** a 76×57 mm image at 180 dpi gives 404 rows and 116k dot lines. The text file is 1.3 MB.

## Our own additions (not yet run on the machine)

These use only the commands above, put together in ways the captures don't show yet:

- **Focus offset per layer** (and depth slices following the floor down): the same relative Z move as step-down (`G102` / `G91` / `G0Z<mm>F600` / `G90` / `G103` / `G0F180000`, then `# MUST`), written between blocks whenever the next block's offset differs. + offset = head lower (`G0Z-…`). At the end of the job the head goes back by the total.
- **Turning per pass**: a fill whose lines turn on each pass can't use the `G104`/`G105` loop (it repeats one pattern), so its passes are written out one after another, each at its own angle.
- **Depth slices**: each slice is an ordinary fill block (`BITMAP HEAD`, `bitmapMode` grayscale, `S` on the burned stretches), with the lines worked out from a grid of cells instead of outlines.
- **Offset fill**: the loops of one shape go in one fill block, each loop traced closed with `S` on and joined by `S0` moves; `density` is 1 / loop spacing.

- **Sections** (designs bigger than the field): each block is cut to the section's rectangle and moved into the field. Fills keep their whole outline and are clipped line by line, so the lines meet across sections.

## Rotary and conveyor (not yet run)

Both swap one galvo axis for the mechanical **U** axis; the machine coordinates the moves.

- **Rotary** (`LASER_CYLINDER`): design X → galvo `X`, design Y → `U` in mm of the object's surface (we put U 0 at the design's middle row). Head after `G0 X0 Y0`: `M535U<scale>` (rollers 0.59917 on an RA2, ×4 on an RA3; chuck 128 ÷ circumference), `G100`, with the galvo Y parked on the rotary line both before and after `G100` (the Laser line setting, default 110 = mid-field; it's the real field's Y, not the unrolled height). `# gc` keys `["x","u"]`, `rm` −1 for rollers, +1 for the chuck. Moves are `G1X…U…`.
- **Rotary speed limit**: the head's `G0 F180000` rapid would spin a rotary dozens of turns a second (it made Kyle's direct-drive chuck take off, 2026-11-08). On the rotary PhotonCanvas writes `G0F<cap>` straight after `G100` (and again after each Z move's `G100`, since the Z block puts `G0F180000` back) and holds every layer's feed to the same cap: half a turn of the object a second (`Job.MaxRotaryTurnsPerS`, cap = 0.5 × circumference × 60 mm/min). Picture dots keep their own feed (the rotary only steps between rows with `G0`).
- **Conveyor** (`CONVEYOR_EXTENSION`, up to 610 mm): design X → `U` (U 0 = mid-field), design Y → galvo `Y`, galvo X parked mid-field. Head: `G100 F9600`, `M535U<0.74592 × 100 ÷ calibration %>`, `M536U<angle compensation>`. Engraving lines run along Y.
- **Tail** (both): `G0 U0`, `G101` straight after `# … TAIL`, then the usual lines.
- **Dots**: the attachment steps with `G0U…` between rows; the galvo fires `G25` along its own axis.
- **Z moves** leave and re-enter U mode: `G101`, the usual Z block, `G100`.
- `description.json`: `mode` `LASER_CYLINDER` / `CONVEYOR_EXTENSION`, `axis` `U`.
- Framing with an attachment only traces the galvo's own direction (a thin box mid-field).
- **Turning the rotary on its own**: `G0 U…` sent from the console outside a job does nothing. What works (Kyle's F2 Ultra, 2026-11-07) is the conveyor feed request `PUT /v1/peripheral/param?type=conveyor`: `{action:"lock"}` first (the motor holds; without it nothing moves), then `{action:"goto", u, speed}` turns it **by** u each time (not to a position: a second `goto 5` turns again, `goto 0` does nothing), `"stop"`, `"free"` (limp). `type=rotary` is refused ("invalid type"). u is in the feed's units: 5 turned a 32-units-a-turn chuck about 45°, so the machine seems to scale the feed by its belt factor (≈ 0.746). PhotonCanvas turns this way and corrects the scale from a one-turn check; if refused, it falls back to a laser-off job uploaded with `autoStart: 1` (header, rotary head, one `G0U<mm>`, the tail without `G0 U0`).

## Step-down per pass ("focus descent") and wobble (captured 2026-10-14)

From xTool Studio exports of a 20 mm square, blue cut 70% 40 mm/s × 3 (`captures/gc/blue_cut_70p_40mms_3pass*.gc`) and red cut with wobble (`red_cut_70p_40mms_3pass_wobble_0.05_0.015.gc`).

- **Step-down** replaces the `G104 P3 … G105` pass loop with the passes written out. The head moves are relative Z, wrapped as `G102` / `G91` / `G0Z<mm>F600` / `G90` / `G103` / `G0F180000`. Before pass 1 it drops by the "first" value (0.01 by default), before each later pass by the per-pass value, and after `# motion_end` it rises by the total, followed by `# MUST`. The first pass has an extra `# MUST` + `G0` to the start point. PhotonCanvas reproduces this line for line (`SampleTests.BlueCut3PassesWithStepDown`). In whole-job pass mode it lowers to that round's depth before the block and rises straight after, so other layers keep their focus.
- **Wobble** is not a firmware feature. The path is expanded into loops: radius = diameter/2, 36 points per loop turning −10° per point (starting at −100°), the loop centre advancing `spacing/36` along the path per point. For 0.05 / 0.015 mm that is ~2400 points per mm. PhotonCanvas matches xTool's 192,000 points to within 0.012 mm (`SampleTests.RedCutWithWobbleMatchesPointByPoint`). Fiber (red) only.
